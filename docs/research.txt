You’re describing something more interesting than “APL with a few neural-network functions.” The coherent version is a new array language whose notation deliberately sits between APL and mathematical ML notation:

APL-style right-to-left evaluation and array semantics.
APL2-style nested arrays as the basis for structured data.
ML primitives that operate on whole tensors/models/parameter structures.
A second, spatial mathematical surface syntax for expressions such as sums, products, gradients, losses, and indexed tensor equations.
Tooling that makes glyph entry practical rather than nostalgic.

I would separate the idea into three layers, because trying to solve all of them in one grammar would likely make the language incoherent.

1. The core language: “APL for tensors”

The core should remain recognizably APL.

That matters because your current sw-apl already gives you the hard parts: a clean-room Rust interpreter, genuine glyph syntax, right-to-left evaluation, arbitrary-rank arrays, a browser implementation, Espanso/Emacs input, workspaces, and regression/conformance infrastructure. Its main historical limitation for this experiment is intentional: it models APL\360 / 5100-era APL rather than APL2, so it currently has flat arrays, no nesting, and no Each.

By contrast, sw-cor24-apl has already explored exactly two features that become important here: nested/boxed arrays and Each, while retaining a right-to-left recursive-descent parser.

That suggests:

Do not mutate historical sw-apl into ML-APL. Fork the semantic architecture and create a new language mode/project.

Call the research language M, L, or APLML; keep sw-apl historically disciplined.

My preference for the actual language name is M.

It fits the Iverson-family tradition:

A → J → K → … → M

and “M” can quietly stand for Machine, Model, Matrix, or ML, without making the language name cumbersome.

APLML would be the better descriptive repo name initially, though:

sw-aplml

with:

Language: M
Tagline: an array language for machine learning

That avoids trying to own an unsearchable one-letter repository.

2. Don't make relu, softmax, etc. merely funny spellings

This is the most important design decision.

Something like:

Y ← relu W+.×X

becoming:

Y ← ♢ W+.×X

doesn't really create a new language. It saves characters.

Instead, ML primitives should exploit APL-level semantics.

For example, classic APL already gives you a concise linear layer:

B + W +.× X

depending on axis convention.

So Linear does not necessarily deserve a primitive glyph at all. Its value is primarily as a parameterized/model object, not as a mathematical operator.

Likewise ReLU is already conceptually:

0⌈X

and sigmoid can be defined compositionally.

This gives you a useful rule:

A primitive earns a glyph only if it introduces a useful semantic concept that is awkward to express compositionally.

For example:

Concept	Existing array expression	New primitive justified?
ReLU	0⌈X	probably no
sigmoid	simple composition	probably no
softmax	possible but verbose + numerically subtle	yes
matmul	+.×	no
convolution	awkward axis/window expression	yes
gradient	impossible as ordinary array primitive	yes
loss	could be library function	maybe
optimizer step	stateful structural transform	yes
attention	composition of common ops	maybe library first
stop-gradient	new AD semantics	yes
parameter	new semantic category	yes
trainable model	structured value	yes

So rather than inventing twenty pictograms for PyTorch functions, create a small ML glyph vocabulary.

3. A proposed ML glyph vocabulary

Unicode already contains a very large mathematical operator repertoire, but Unicode explicitly does not assign unique semantics to every mathematical use; applications/languages decide those meanings in context.

That means you can use existing Unicode characters rather than inventing a custom font.

I would begin with about six new semantic primitives.

Glyph	Spoken form	Meaning
∇	grad	derivative / gradient
⨂	tensor	tensor/outer interaction, if not conflicting with APL outer product
⧉	window	sliding window / convolution operand
⌁	soft	normalize logits / softmax-like transform
⚿ or another safe glyph	param	trainable parameter
↻	step	optimizer state transition

I'm intentionally not strongly endorsing those exact glyphs yet. Glyph selection should come after the semantic inventory, because visually clever symbols become regrettable language syntax.

One especially good candidate is:

∇

because ML users already understand it.

Example:

G ← ∇ Loss Params

or, preserving stronger APL dyadic structure:

Params ∇ Loss

But I would actually treat ∇ as an operator, not a function:

∇Loss Params

meaning:

derive the gradient function of Loss, then apply it to Params.

That is much more Iversonian.

4. Operators are probably more important than new functions

This is where the language could become genuinely distinctive.

APL's superpower isn't merely arrays. It is that functions can be transformed by operators.

Machine learning is full of function transformations:

differentiate a function
vectorize a function
batch a function
checkpoint a function
jit/compile a function
map over devices
calculate value-and-gradient
attach trainable parameters
freeze part of a model

These map beautifully onto the APL operator concept.

For example, conceptually:

∇F

gradient of F

⌸F

batched/vectorized F

F¨

Each, already familiar from modern APL

F⍤R

rank-sensitive application

and potentially:

F⍢

training/update transformation

So an optimizer might not be:

adam(model, gradients)

but:

Params ← Rate Adam Loss Params

or even an operator-derived training verb:

Train ← Adam⍤Loss
Params ← Train Params Batch

The exact notation needs experimentation, but this direction is stronger than assigning Adam a decorative Unicode glyph.

5. The real breakthrough: make mathematical notation another surface syntax

Your multiline idea is potentially the differentiator.

Don't try to force two-dimensional mathematics directly into the ordinary APL lexer.

Instead build:

          ┌─────────────┐
APL glyph │             │
source ──▶│             │
          │ semantic IR │──▶ evaluator
Math 2D ─▶│             │
source    │             │
          └─────────────┘

APL syntax and mathematical notation are then two parsers for one expression IR.

That is very similar philosophically to what web-sw-cor24-apl already does in the other direction: it can display the same operations as representative ASCII words, APL glyphs, or literate descriptions.

You would extend that idea from display aliases to actual bidirectional notation.

6. Do not encode 2-D math as fake lines of text

For example, this:

$$ \operatorname{softmax}(z)_i = \frac{e^{z_i}} {\sum_{j=1}^{K} e^{z_j}} $$

cannot robustly be represented by counting spaces in:

              e^zᵢ
    ----------------------
        K
        Σ     e^zⱼ
       j=1

unless the editor owns the layout.

Unicode itself distinguishes between character encoding and higher-level mathematical composition; MathML/TeX-like systems provide structure that plain Unicode doesn't.

So I would borrow the best DiscoveryOne idea:

position is syntax, but serialize position explicitly.

DiscoveryOne already proposes source objects with (x,y,z) coordinates and semantic facets. You only need (x,y) for mathematics.

Internally:

struct MathGlyph {
    text: String,
    x: i32,
    y: i32,
}

but very quickly parse those into structural nodes:

Fraction
 ├─ numerator
 │   └─ Exp(Index(z,i))
 └─ denominator
     └─ Sum
         ├─ binder: j
         ├─ lower: 1
         ├─ upper: K
         └─ Exp(Index(z,j))

That becomes:

Expr::Div(
    Exp(Index(z,i)),
    Reduce {
        op: Add,
        binder: j,
        range: 1..K,
        body: Exp(Index(z,j))
    }
)

And then lower it to APL-array semantics.

That separation is crucial.

7. Math notation → array algebra should be visible

This would make an excellent teaching/research environment.

Input:

$$ y_i = \frac{e^{x_i}}{\sum_j e^{x_j}} $$

Compiler interpretation:

index notation
      ↓
axis semantics
      ↓
array algebra
      ↓
M/APL source

For example, conceptually:

E ← * X - ⌈/X
Y ← E ÷ +/E

The user could switch among:

paper math
indexed math AST
APL/M expression
shape trace
evaluated arrays

That dovetails extremely well with what you're doing in MLPL and the “learn visually” direction.

And it gives the project an educational purpose larger than “APL with ML built-ins.”

8. Mathematical binders should be first-class compiler constructs

Sums and products are not merely glyphs.

This:

$$ \sum_{i=1}^{n} x_i $$

contains:

operator      Σ
binder        i
lower bound   1
upper bound   n
body          x_i

So parse it initially as:

Reduce {
    op: Sum,
    variable: i,
    domain: Range(1,n),
    expr: x[i],
}

Then perform an arrayification pass.

If i indexes the only axis of x:

Σᵢ xᵢ

becomes:

+/X

For:

$$ y_i = \sum_j W_{ij}x_j $$

the compiler can recognize contraction:

contract axis j

and lower to an inner product / matrix-vector operation.

This would be an outstanding feature because users could see:

loops → indexed mathematics → contractions → array combinators

which is essentially the conceptual bridge between conventional ML notation and APL.

9. Add Einstein notation before adding dozens of ML built-ins

I'd prioritize this surprisingly highly.

For example:

$$ C_{ij} = \sum_k A_{ik} B_{kj} $$

should become something structurally equivalent to:

C ← A +.× B

Likewise common tensor contractions could be inferred from repeated bound indices.

That means your language has something resembling:

math compiler
    ↓
index contraction
    ↓
APL array algebra

This is much more interesting than:

matmul(A,B)

And it fits your previous work translating CNN formulas to MLPL exceptionally well.

10. Tuples: yes—but don't confuse tuples with nested arrays

Your secondary question deserves a firm distinction.

APL2 already provides extremely powerful recursive heterogeneous structure: nested arrays may contain arrays of differing shape, rank, depth, and type.

So this:

(Weights Bias)

can already conceptually be represented as a nested array.

But a tuple should convey something different:

fixed-position product structure whose elements do not participate in ordinary array scalar extension/broadcasting as one homogeneous array.

For ML this matters greatly.

A layer may return:

(output, state)

An optimizer step may return:

(params, optimizer-state)

A training iteration might yield:

(loss, params, metrics)

Treating those as an ordinary nested vector is semantically weak.

So I would have three fundamental structural categories:

Scalar
Array
Tuple

with arrays recursively allowed to contain boxed/nested values if desired.

11. Make tuples named products, inspired by DiscoveryOne/Tuplet

DiscoveryOne's ancestry is relevant because Tuplet/DiscoveryOne treats named tuples and multi-output verbs as fundamental.

For M, I would simplify the idea.

For example:

R ← ⟨Loss Params Metrics⟩

or constructor syntax:

⟨loss: L, params: P, metrics: M⟩

and selection:

R.loss

You don't need to force tuple semantics into APL indexing.

The semantic distinction becomes:

Structure	Meaning
array	many things of the same structural axis space
nested array	array whose cells may themselves be arrays/objects
tuple	one product value consisting of distinct roles
named tuple	tuple with semantic fields

That distinction is extremely useful for ML.

Consider Adam state:

AdamState =
    ⟨step,
      first_moment,
      second_moment⟩

Those values are structurally related but are not an array.

12. Tuples solve a longstanding awkwardness in array languages

APL is excellent when one answer is an array.

Modern computation often wants multiple semantically different outputs.

Instead of conventions such as:

2⊃R

you could have:

R.params
R.loss

or destructuring:

⟨L P S⟩ ← Train Batch State

This would fit right-to-left evaluation nicely:

⟨Loss Params State⟩ ← Batch Train State

A function can remain conceptually monadic/dyadic yet return a product.

This is one place where I think departing from traditional APL is worth it.

14. Shape should be part of the language's explanatory model

APL already makes shape fundamental through ⍴.

ML should take that further.

For example a smart editor could show:

Y ← W +.× X

with hover metadata:

W : 768 × 3072
X : 3072 × 128
────────────────
Y : 768 × 128

And math notation:

$$ Y_{ij}=\sum_k W_{ik}X_{kj} $$

could annotate:

i → 768
j → 128
k → 3072 (contracted)

This may be more valuable pedagogically than the ML glyphs themselves.

15. The editor is part of the language

APL historically required specialized input.

You've already solved much of that problem in sw-apl: the browser has an APL keyboard, and the project explicitly supports Espanso and Emacs keymaps.

For M I would make this a first-class design principle:

Source remains Unicode text, but editing is mnemonic.

Example Espanso mappings:

\grad     → ∇
\rho      → ⍴
\iota     → ⍳
\each     → ¨
\sum      → ∑
\product  → ∏
\alpha    → α
\partial  → ∂

Maybe use an APL-style prefix key:

Alt-G G   → ∇
Alt-G R   → ⍴

but Espanso provides the portable baseline.

The editor should then display:

∇
Gradient operator
Derives a function computing ∂output/∂argument

on hover.

That largely eliminates the classic “APL hieroglyphics” objection.

16. Make glyphs readable without changing source

Borrow directly from web-sw-cor24-apl.

It already supports:

representative syntax
APL glyph syntax
literate syntax

Extend that to four synchronized views:

Glyph
    ∇Loss P

Mnemonic
    grad Loss P

Literate
    gradient-of Loss applied-to P

Mathematical
       ∂ Loss
    ─────────
       ∂ P

All four views point at the same AST.

That is a much stronger UI than a syntax highlighter.

17. Don't parse arbitrary printed mathematics in M0

There is a large difference between:

“our editor understands structured two-dimensional math”

and:

“paste arbitrary mathematics from a paper and we'll parse it.”

The latter rapidly becomes an OCR/TeX/CAS research project.

For the first version, constrain the grammar to:

fractions
superscripts
subscripts
Σ
Π
∂
∇
parentheses/brackets
indexed variables
equality
common arithmetic
perhaps expectation E
tensor contractions

That is enough for a surprisingly large fraction of introductory ML equations.

Softmax alone is a good proof:

$$ \sigma_i(z)=\frac{e^{z_i}}{\sum_{j=1}^{K} e^{z_j}} $$

Google's ML material uses essentially this standard formula.

18. The first demonstration should be softmax

It exercises nearly everything you care about.

Start with the paper notation:

$$ s_i = \frac{e^{z_i}} {\sum_j e^{z_j}} $$

Then show its interpretation:

numerator
    exponent(index(z,i))

denominator
    reduce(add, j, exponent(index(z,j)))

Then arrayify:

E ← *Z
S ← E ÷ +/E

Then stabilized version:

E ← *Z-⌈/Z
S ← E÷+/E

Then replace the implementation with a primitive if desired:

S ← ⌁Z

Clicking ⌁ could expand back into its definition.

That gives you a beautiful distinction between:

primitive as abstraction

and

array expression as explanation

19. Second demo: a linear layer should deliberately have no glyph

Math:

$$ y = Wx+b $$

M:

Y ← B + W +.× X

This demonstrates the opposite lesson:

APL already is an ML notation when the operation is fundamentally array algebra.

That's important intellectually. Otherwise the project risks seeming like a Unicode façade over a tensor library.

20. Third demo: gradient descent

Math:

$$ \theta_{t+1} = \theta_t-\eta\nabla_\theta L(\theta_t) $$

M might look like:

Θ ← Θ - η × ∇Loss Θ

That is where the ML extension pays for itself.

And then:

Train ← {
    Θ ← Θ - η × ∇Loss Θ
}

or an eventual derived optimizer form.

21. Fourth demo: Adam shows why tuples matter

Adam has:

parameters
first moment
second moment
step
hyperparameters

So something like:

State ← ⟨step:0 m:0×Θ v:0×Θ⟩

then:

⟨Θ State⟩ ← Grad AdamStep ⟨Θ State⟩

This makes the tuple work clearly justified rather than an arbitrary language feature.

22. Fifth demo: CNN equation → array operation

Use one of the nested-sum convolution equations you've been exploring.

Something like:

$$ Y_{i,j,k} = \sum_m\sum_n\sum_c X_{i+m,j+n,c}K_{m,n,c,k} $$

Your math parser recognizes:

free indices:      i j k
contracted:        m n c

and lowers it to:

window + contraction

Then either:

Y ← K Conv X

or a composition of window and inner-product primitives.

This would connect directly to the CNN/math work in MLPL.

25. Autodiff should be phase 2, but architect for it immediately

If ∇ is going to mean anything beyond symbolic rewriting, every primitive eventually needs derivative metadata.

For instance:

Primitive {
    eval
    shape_rule
    derivative_rule
}

Conceptually:

Add
  eval:       x+y
  shape:      broadcast(x,y)
  derivative: (dx,dy) → dx+dy

This gives you:

evaluation
shape inference
automatic differentiation
documentation

from the same primitive registry.

That registry could be the heart of the language.

26. I'd make primitives declarative

For example, conceptually:

primitive softmax {
    glyph:    "⌁"
    name:     "softmax"
    arity:    1
    rank:     last-axis
    shape:    identity
    expand:   exp(x-max(x)) / sum(exp(x-max(x)))
    grad:     ...
}

Then the browser can generate:

tooltip
help
mnemonic entry
pretty rendering
shape rule
expansion
tests

from one definition.

This would be a good evolution beyond both current APL implementations.

I would resist merging the two.

They serve different pedagogical purposes.

MLPL
Readable
word-oriented
explicit
good for stepping through concepts
approachable
M
dense
symbolic
array-first
close to mathematical notation
composition-oriented

They can share the semantic ML layer.

For example:

MLPL:
softmax logits

M:
⌁Z

Math:
        eᶻⁱ
──────────────────
   Σⱼ eᶻʲ

All could lower to something like:

MlOp::Softmax(axis=-1)

That creates an unexpectedly useful architecture:

MLPL and M become two experimental languages over the same ML semantics.

31. What I would not do

Avoid these early:

40 new ML glyphs.
GPU support.
full PyTorch compatibility.
general symbolic algebra.
arbitrary LaTeX import.
arbitrary handwritten/pasted math recognition.
static dependent tensor types.
trying to run existing Python models.
modifying historical sw-apl semantics.
giving every named ML function a primitive.

Those are distractions from the distinctive idea.

The research question should instead be:

Can mathematical ML notation be mechanically transformed into concise array-language programs, while retaining an executable connection between the notation, shapes, intermediate arrays, and learning process?

That is a crisp and unusual project.

That gives M an unusual design principle:

If the runtime can execute a primitive but Rosetta cannot explain its structure, data movement, provenance, and transformation, the primitive is incomplete.

That could be one of the defining rules of the project.

63. The larger idea

This changes how I'd describe the entire project.

Initially we had:

M is an APL2-inspired array language for machine learning.

Now I'd describe it as:

M is an observable array language for expressing machine learning in executable mathematical notation. M Rosetta lets the same computation be explored as mathematics, array notation, structure, live data, and machine execution—across time and levels of abstraction.

That is a considerably stronger research idea.
